# Operational metric foundation

Issue #162 defines version `2026-09-11.3` for the current-work projection used by later SLA and routing work. It is an authenticated server-side projection, not an analytics dashboard or a performance score.

`currentWork.total` counts visible tenant tickets whose *current* status is `open` or `pending`. Its numerator is that set; its denominator is the same set at one D1 statement snapshot. `unassigned` is the same denominator with a null assignee; `assigned` is `total - unassigned`. A staff administrator sees the tenant's visible records. An agent sees ungrouped tickets and tickets for groups where current `user_groups` membership authorizes that agent. Customer and integration scopes are rejected. The projection accepts no tenant, actor, group, status, time, or resource selector from a caller.

The projection verifies the current user role and session version inside the same D1 statement as the data read. It therefore rejects a stale staff scope after a role or session revocation, while the statement's group predicate applies current membership. System scopes are limited to trusted server workflows.

The projection is evaluated from `tickets` on every read. `asOf` and `freshThrough` are issued by a server-owned clock; a caller cannot supply a future timestamp. Consumers evaluate the receipt against their trusted server clock and must rebuild after `freshThrough` (60 seconds). A serialized receipt never changes its own freshness state.

Before actor or group filtering, the statement materializes at most 1,001 tenant ticket candidates in tenant/id order and at most 1,001 tenant event candidates in tenant/ticket/sequence order (the 1,000-record limit plus one overflow sentinel). Both candidate reads use covering indexes, so sparse group visibility cannot cause a full-tenant ticket scan or an unbounded event sort. A tenant-ticket candidate cap produces `currentWork.status: "truncated"` with reason `tenant_ticket_candidate_cap_exceeded`, null totals, and an empty assignee list. It also makes the canonical-event receipt truncated because the visible ticket set is incomplete. A tenant-event candidate cap produces `canonicalEvents.status: "truncated"` with reason `tenant_event_candidate_cap_exceeded` and null event totals. These receipts disclose no candidate or hidden-row detail and never present partial values as tenant-wide totals. The `byAssignee` list is capped at 100 entries and explicitly reports output truncation only when the current-work total remains available. It is a routing input only: it contains current assignment counts and does not contain historical throughput, quality, ranking, targets, or employee scoring.

`canonicalEvents.total` counts persisted `conversation_events` joined through the same authorized ticket set. It reconciles known synthetic fixture intake events with the current-work projection without treating events as an alternative current-state store. Canonical events have server `recorded_at`, but no provider occurrence time, so `lateOrReplayed` is `not-derived`. A late persisted event is included when the projection is rebuilt. Accepted mutation replays retain the original receipt and create no second canonical event.

SLA metric contracts are already fixed even though their values remain unavailable: first response is the count of tickets with an eligible first staff response at or before a configured response deadline over tickets with accepted intake, a configured SLA policy, and a deadline in the selected window; resolution uses the equivalent resolution deadline. Both require server-recorded canonical time plus the calendars, pause, and waiting semantics owned by #73/#136.

Routing metric contracts are also fixed: assignment load is visible current-work tickets assigned to an actor over visible current work at the same snapshot; eligible capacity is candidates with remaining configured capacity over candidates with current availability, group eligibility, and a configured ceiling. Availability leases, ceilings, fairness, and routing decisions remain unavailable until #137. Consumers must surface those states as unavailable, rather than calculate an implied SLA, capacity, or individual performance metric.
