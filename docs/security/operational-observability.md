# Operational observability contract

Issue #159 adds a versioned, allowlisted runtime event envelope for active HTTP paths. It records a correlation ID, normalized route, method, outcome, status and latency only. The serialization boundary normalizes unknown routes/methods, validates UUID correlation IDs and finite nonnegative latency, derives outcome from a valid HTTP status, and drops every extra property. It does not accept arbitrary attributes and must never include authentication headers, cookies, OTP or magic-link material, API keys, channel credentials, provider payloads, ticket/article/attachment content, or AI prompts/outputs.

Canonical D1 audit remains the non-sampled evidence owned by #63. This diagnostic envelope is separate, can be sampled only under a later approved retention policy, and does not provide tenant analytics (#85) or customer diagnostic context (#92).

Local persistence is off. Emission requires `OBSERVABILITY_MODE=isolated-evidence` and either the existing non-production `LOCAL_BETA_ENABLED=true` environment or explicit `ENVIRONMENT=test`. The test opt-in permits synthetic background-operation evidence without enabling local-beta workflows; the workflow local-beta prohibition remains unchanged. No checked-in deployment configuration is enabled by this test-only opt-in. Production is disabled pending #42 verification of access, retention, sampling and redaction. Telemetry failure is swallowed after the request outcome is set; it cannot bypass authentication, tenant isolation, durability, approval or recovery.

Initial SLI evidence is recorded as machine-readable JSON with revision, tool versions, environment, route class, request count, latency percentiles and failure counts. Do not ratify global thresholds from synthetic data. Preserve #51's separate measured 50 ms warm-ingress target. Isolated evidence now covers trusted and pre-tenant D1 resolution, tenant-qualified and legacy default-tenant R2 reads/deletes, realtime ingress and fresh NotificationDO session revalidation. D1 `all`/`run` result envelopes and batches with `success:false`, plus resolved DO 5xx responses, are fixed failure outcomes without changing the original result or retry behavior. Request-scoped auth/canonical mutation summaries remain bounded local evidence; fleet aggregation is not claimed. Future pipeline integration follows #51/#91/#87/#88; those implementations are not prerequisites for this issue’s extension contracts.

Alert runbooks must cover DLQ/quarantine, oldest pending journal/outbox age, dispatch uncertainty, sustained active-path errors and budget-admission failures. Include diagnostic event volume and retention in #50/#64 accounting before enabling any non-local evidence channel.

## Bounded local collector and export — 10 September 2026

`createLocalObservabilityCollector` is a caller-owned in-memory diagnostic sink for synthetic local evidence. It has no Worker binding, file, network transport, timer, global registry or automatic retention. Its memory lifetime follows caller-held collector and exported-snapshot references; it provides no secure-erasure guarantee. It is not wired into production configuration and does not alter canonical D1 audit, admission, request authorization, or application error behavior.

The collector reconstructs only current-version (v1) HTTP and resource envelopes before retaining them, dropping invalid, unknown or unsupported-version input and every extra property. It stores at most 64 events and 16 KiB by default; callers may choose only bounded limits up to 256 events and 64 KiB. `maxBytes` counts UTF-8 JSON payload bytes for retained event envelopes only; it does not represent the wrapper's serialized size or JavaScript heap use. It samples deterministically by retaining every Nth validated event, beginning with the first. Retention is first-fit: a later event can never evict an earlier one. Exports contain the fixed retention contract and separate attempted, retained, invalid, sampled-out, event-limit and byte-limit counts. `complete: false` means that any input was omitted. A snapshot never becomes billing usage, a complete SLI denominator, tenant analytics, or canonical audit evidence.

`npm run test:local-observability-collector --workspace=apps/server` uses a synthetic Hono request flow with the real middleware and injected local sink. It proves responses remain successful while a two-event collector exports only route/method/status allowlisted envelopes and reports the third event as an explicit limit drop. Focused collector tests cover allowlist reconstruction, invalid input, deterministic sampling, event/byte limits and option bounds. This is #159 local evidence of caller-owned retention and sampling behavior; production retention, access governance and non-local sampling remain gated by #42.

## Request credential SLI

The existing isolated-evidence gate now creates one request-owned `auth.sli.request` credential counter. Staff `authMiddleware` records one decision after current tenant/user/session-version/role checks: accepted with the signed MFA-verified claim, or challenge without it. API-key middleware records accepted only after its active hashed-key resolution; widget/customer middleware records accepted only after its signed widget claims plus current tenant/user/email/role/session checks. Password login records `challenge` only after a valid password has minted a short-lived MFA challenge, and `accepted` only after a valid password has minted a full app token. MFA verification records `accepted` only after a current challenge and valid code mint a full app token. Customer verification records `accepted` only after its tenant-scoped opaque credential was consumed and a widget token was minted. Realtime records the current MFA-complete agent/admin app credential before local admission and Durable Object forwarding. Explicit malformed/revoked credentials and current identity mismatches are denied; missing database, resolver faults and unexpected verifier, crypto or token-mint failures are unavailable. The existing HTTP responses and authorization sequence remain unchanged. **Accepted describes the credential decision, not permission to perform the requested action**: local-beta admission, route authorization and MFA enforcement remain separate gates. A valid tenant-A widget credential receiving a tenant-B resource 404 remains accepted authentication, not denial. It does not classify a later handler error as failed authentication.

Counts are fixed, unsampled within that one recorded decision, and contain no IDs, credentials, route, raw status or error. Duplicate/invalid records or observer faults mark the in-memory evidence incomplete. A snapshot is immutable point-in-time evidence: a later asynchronous sink failure does not rewrite an already exported copy or prove delivery. Initialization/transport failure can omit output; a missing snapshot is never a successful decision. There is no fleet-wide complete denominator, durable collection or unsampled transport claim.

At most one additional summary is attempted per request where a credential gate records a decision. The shared accumulator detects overlapping credential gates: a second record marks evidence incomplete rather than silently counting twice. It is separate from the intentionally sampled HTTP/resource collector. `estimateDiagnosticEnvelope` reserves H+A+M+64×(C+D+B) potential log events after the canonical extension below (A and M each default conservatively to H, and each cannot exceed H; C defaults to H while D/B are explicit). No trace transport is active. Health, anonymous widget configuration, malformed request bodies, rate-limit responses, customer `/auth/request` acknowledgements, and MFA enrollment mutation/issuance have no new credential decision. In local beta, an admission-suppressed password or customer verification preserves its existing enumeration-safe response but records no credential result, because admission occurs before the password verifier or opaque-token consume. The resource-bound field is `credentialAuthRequests`, covering all credential gates; its numeric bound remains unchanged.

Validation includes the real two-tenant Miniflare credential fixture: a valid API key is accepted, a valid tenant-A widget credential is accepted while a tenant-B resource remains hidden, and revoked API-key/widget credentials are denied. Its password/MFA path observes a password step-up, completed MFA, a revoked challenge denial, and customer opaque-token verification while the preceding customer auth-request acknowledgement emits no credential summary. A throwing optional auth observer leaves an accepted API request successful. Focused tests distinguish disallowed signing algorithms, unavailable database, realtime resolver failure, step-up and observer rejection. MFA enrollment mutation/issuance, full local-beta admission, and durable mutation failure acceptance remain outside this credential SLI. Production telemetry remains #42.

## Canonical mutation request SLI

The same isolated-evidence gate now creates one request-owned `canonical_mutation.sli.request` accumulator. It is used only at current trusted canonical ticket-mutation boundaries: API and portal ticket create/reply through `TicketMutationReplayService`; dashboard ticket creation through its tenant-scoped atomic repository batch; audited API/staff ticket PATCH; the tenant-scoped D1 replay repository used for an audited staff reply; and the API reply route's tenant-scoped missing-ticket decision. It contains fixed safe-integer counts only: `attempted`, `durablyCompleted`, `replayed`, `noOp`, `denied`, and `uncertain`. There are no tenant, ticket, article, principal, request, credential, content, status, error, timing, receipt, or audit-event fields.

`attempted` is recorded before constructing the tenant-scoped D1 batch, or when a currently authorized stored receipt has been rendered for replay. `durablyCompleted` is recorded only after that exact D1 batch returns its final nonempty response snapshot. For audited PATCH, the batch's `UPDATE ... RETURNING` row decides the terminal result: a changed row is completed and an unchanged row is `noOp`. An HTTP 200/201, a fulfilled caller promise, later notification/broadcast/email work, or a swallowed handler failure never records completion. A receipt replay is separately `replayed`; it does not claim a new durable write or end-to-end success after arbitrary caller work: a later authority recheck can still reject a caller that already observed a receipt. A known tenant-scoped pre-mutation denial or trusted credential/admission denial is `denied` and has no durable attempt. A batch-construction failure, started D1 batch failure, missing final snapshot, or result that cannot be reconciled to an authoritative winner receipt is `uncertain`; this is a known uncertainty, so its snapshot can still be complete. Invalid sequencing, a missing terminal acknowledgement, or an observer fault marks the in-memory evidence incomplete.

At most one canonical summary is attempted for a request that reaches one of those decisions. It uses the optional unsampled SLI observer (or the guarded application console when no observer is injected), rather than `createLocalObservabilityCollector`: that collector deliberately samples and drops resource envelopes and therefore cannot be an aggregate SLI denominator. The new event bound is M, where `0 <= M <= H` and M is one only for a request with a canonical decision. Together with the existing HTTP/resource and staff-auth summaries, the maximum current application console-event bound is `H + A + M + 64×(C+D+B)`, conservatively no greater than `3H + 64×(C+D+B)` because `A <= H` and `M <= H`. `estimateDiagnosticEnvelope` reserves this combined bound; auth and canonical summaries can coexist on one request, so neither is subtracted from the other. This is planning evidence, not billed usage or durable collection.

Validation uses disposable two-tenant Miniflare replay and audit fixtures with guarded local evidence enabled. The replay fixture observes one real committed receipt, one authorized replay, a tenant-B denial against tenant-A's ticket, and a forced receipt-insert batch rollback as four distinct summaries. The audit fixture observes a real dashboard creation batch, changed dashboard audited PATCH, and unchanged API audited PATCH as separate completed/completed/no-op summaries. Neither fixture serializes synthetic content or tenant identifiers. Focused middleware coverage also proves a rejecting canonical observer cannot replace a 201 response. Raw/system repository callers, standalone ticket/article operations outside these routes, and the separate canonical audit/replay work in #63 remain outside this change. Production telemetry, persisted aggregate denominators, retention, alerting, canonical audit truth and consumer SLO policy remain outside this change.
