# Operational observability contract

Issue #159 adds a versioned, allowlisted runtime event envelope for active HTTP paths. It records a correlation ID, normalized route, method, outcome, status and latency only. The serialization boundary normalizes unknown routes/methods, validates UUID correlation IDs and finite nonnegative latency, derives outcome from a valid HTTP status, and drops every extra property. It does not accept arbitrary attributes and must never include authentication headers, cookies, OTP or magic-link material, API keys, channel credentials, provider payloads, ticket/article/attachment content, or AI prompts/outputs.

Canonical D1 audit remains the non-sampled evidence owned by #63. This diagnostic envelope is separate, can be sampled only under a later approved retention policy, and does not provide tenant analytics (#85) or customer diagnostic context (#92).

Local persistence is off. Emission requires `OBSERVABILITY_MODE=isolated-evidence` and either the existing non-production `LOCAL_BETA_ENABLED=true` environment or explicit `ENVIRONMENT=test`. The test opt-in permits synthetic background-operation evidence without enabling local-beta workflows; the workflow local-beta prohibition remains unchanged. No checked-in deployment configuration is enabled by this test-only opt-in. Production is disabled pending #42 verification of access, retention, sampling and redaction. Telemetry failure is swallowed after the request outcome is set; it cannot bypass authentication, tenant isolation, durability, approval or recovery.

Initial SLI evidence is recorded as machine-readable JSON with revision, tool versions, environment, route class, request count, latency percentiles and failure counts. Do not ratify global thresholds from synthetic data. Preserve #51's separate measured 50 ms warm-ingress target. Tenant-composed D1 invocations and tenant-qualified attachment R2 calls now emit bounded operation envelopes in isolated evidence mode. Remaining hooks: pre-tenant/legacy-R2 operations and aggregate auth/canonical-mutation SLIs. Future pipeline integration follows #51/#91/#87/#88; those implementations are not prerequisites for this issue’s extension contracts.

Alert runbooks must cover DLQ/quarantine, oldest pending journal/outbox age, dispatch uncertainty, sustained active-path errors and budget-admission failures. Include diagnostic event volume and retention in #50/#64 accounting before enabling any non-local evidence channel.

## SLI definitions and collection status

These are the initial collection contracts, not ratified production promises. Use a five-minute operational window and a one-hour comparison window for rates; performance receipts also retain their exact bounded sample window. A zero denominator means **no observations**, never 100% availability. Record attempted/completed/failed counts separately so missing completions are visible. Percentiles use completed observations with the sample count and failure count alongside them; failure latency is not silently dropped. Unsampled audit remains separate.

| Path | Denominator and success numerator | Other observations and current collection status |
|---|---|---|
| API | Requests received / requests with an expected terminal outcome. Expected denials are distinguished from unexpected 5xx and transport failures. | Route-class latency and outcomes exist in the HTTP envelope; the local receipt checks explicit expected status for three scenarios. Fleet-wide aggregation is pending. |
| Authentication | Authentication attempts / correctly completed decisions; rejection rate is a separate signal, not automatically an availability failure. No identifiers, submitted tokens or codes. |

## Alert evaluation and response contracts

These conditions define required signals and response behavior. They do not enable external alerts, assume absent collectors are healthy, or ratify numeric global thresholds. Until a collector exists, report **not instrumented**. Thresholds needing a baseline stay explicitly unratified; production activation requires #42.

| Condition | Evaluation | Required response |
|---|---|---|
| DLQ or quarantine | Any newly entered item; retain current depth and oldest age, avoiding repeated notifications for the same unchanged state. | Inspect the protected recovery record with authorized tooling; identify the category, fix the cause and use the owning pipeline's bounded replay. Never log its payload or force acknowledgement. |
| Oldest pending journal/outbox age | Oldest eligible pending age exceeds that pipeline's approved recovery target. Exclude documented scheduled-not-before waits; separately show blocked/unknown states. No approved target means configuration incomplete. | Check dispatcher/consumer availability, admission and retry state. Preserve durable intent; do not delete old records to make the signal green. |
| Dispatch uncertainty | Any new uncertain provider outcome; unresolved age remains visible. | Reconcile using #88's provider/idempotency contract. Never blindly resend, mark delivered, or bypass approval because telemetry is inconclusive. |
| Sustained active-path errors | Unexpected failure numerator/attempt denominator in consecutive five-minute windows exceeds a baseline-ratified threshold, with the configured minimum sample count. Threshold/sample count are not yet ratified. | Compare the one-hour window and recent changes; verify auth and durability remain intact. Diagnose through safe categories and protected audit; do not disable those controls to restore a success rate. |
| Budget admission failures | Count intentional exhausted-budget denials separately from admission-service failures. Alert on a newly broken admission path; sustained denials use an approved tenant budget policy. | Check #50/#64 reservation/settlement and capacity state. Do not silently raise limits, spend paid capacity or fail open. |
| Missing telemetry | Expected collector heartbeat/receipt absent for its configured interval, or an invalid/incomplete receipt. | Report observability unavailable and investigate collection independently. Absence of telemetry does not prove service health or authorize state repair. |

## Bounded local collector and export — 10 September 2026

`createLocalObservabilityCollector` is a caller-owned in-memory diagnostic sink for synthetic local evidence. It has no Worker binding, file, network transport, timer, global registry or automatic retention. Its memory lifetime follows caller-held collector and exported-snapshot references; it provides no secure-erasure guarantee. It is not wired into production configuration and does not alter canonical D1 audit, admission, request authorization, or application error behavior.

The collector reconstructs only current-version (v1) HTTP and resource envelopes before retaining them, dropping invalid, unknown or unsupported-version input and every extra property. It stores at most 64 events and 16 KiB by default; callers may choose only bounded limits up to 256 events and 64 KiB. `maxBytes` counts UTF-8 JSON payload bytes for retained event envelopes only; it does not represent the wrapper's serialized size or JavaScript heap use. It samples deterministically by retaining every Nth validated event, beginning with the first. Retention is first-fit: a later event can never evict an earlier one. Exports contain the fixed retention contract and separate attempted, retained, invalid, sampled-out, event-limit and byte-limit counts. `complete: false` means that any input was omitted. A snapshot never becomes billing usage, a complete SLI denominator, tenant analytics, or canonical audit evidence.

`npm run test:local-observability-collector --workspace=apps/server` uses a synthetic Hono request flow with the real middleware and injected local sink. It proves responses remain successful while a two-event collector exports only route/method/status allowlisted envelopes and reports the third event as an explicit limit drop. Focused collector tests cover allowlist reconstruction, invalid input, deterministic sampling, event/byte limits and option bounds. This is local synthetic evidence only; production retention, access governance, non-local sampling and volume accounting remain owned by #42 and #50/#64.

## Canonical mutation request SLI

The same isolated-evidence gate now creates one request-owned `canonical_mutation.sli.request` accumulator. It is used only at current trusted canonical ticket-mutation boundaries: API and portal ticket create/reply through `TicketMutationReplayService`, the tenant-scoped D1 replay repository used for an audited staff reply, and the API reply route's tenant-scoped missing-ticket decision. It contains fixed safe-integer counts only: `attempted`, `durablyCompleted`, `replayed`, `denied`, and `uncertain`. There are no tenant, ticket, article, principal, request, credential, content, status, error, timing, receipt, or audit-event fields.

`attempted` is recorded before constructing the tenant-scoped D1 batch, or when a currently authorized stored receipt has been rendered for replay. `durablyCompleted` is recorded only after that exact D1 batch returns its final nonempty response snapshot. An HTTP 201, a fulfilled caller promise, later notification/broadcast/email work, or a swallowed handler failure never records completion. A receipt replay is separately `replayed`; it does not claim a new durable write or end-to-end success after arbitrary caller work: a later authority recheck can still reject a caller that already observed a receipt. A known tenant-scoped pre-mutation denial or trusted credential/admission denial is `denied` and has no durable attempt. A batch-construction failure, started D1 batch failure, missing final snapshot, or result that cannot be reconciled to an authoritative winner receipt is `uncertain`; this is a known uncertainty, so its snapshot can still be complete. Invalid sequencing, a missing terminal acknowledgement, or an observer fault marks the in-memory evidence incomplete.

At most one canonical summary is attempted for a request that reaches one of those decisions. It uses the optional unsampled SLI observer (or the guarded application console when no observer is injected), rather than `createLocalObservabilityCollector`: that collector deliberately samples and drops resource envelopes and therefore cannot be an aggregate SLI denominator. The new event bound is M, where `0 <= M <= H` and M is one only for a request with a canonical decision. Together with the existing HTTP/resource and staff-auth summaries, the maximum current application console-event bound is `H + A + M + 64C`, conservatively no greater than `3H + 64C` because `A <= H` and `M <= H`. `estimateDiagnosticEnvelope` reserves this combined bound; auth and canonical summaries can coexist on one request, so neither is subtracted from the other. This is planning evidence, not billed usage or durable collection.

Validation uses the existing disposable two-tenant Miniflare replay fixture with guarded local evidence enabled. It observes one real committed receipt, one authorized replay, a tenant-B denial against tenant-A's ticket, and a forced receipt-insert batch rollback as four distinct summaries; neither synthetic body nor tenant identifier appears in them. Focused middleware coverage also proves a rejecting canonical observer cannot replace a 201 response. This does not cover dashboard ticket creation through the older `createWithInitialArticle` path, ticket PATCH/state changes, raw/system repository callers, or the separate canonical audit/replay work in #63. Production telemetry, persisted aggregate denominators, retention, alerting, canonical audit truth and consumer SLO policy remain outside this change.
