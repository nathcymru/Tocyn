Scope: manual assignment admission and versioned capacity configuration, developed on `436e01d0` and integrated onto signed main `c074805f`. This is not automatic routing, a presence/availability lease, capacity UI acceptance, or Beta.2 clearance.

## Contract and implementation

Capacity is an assignment admission limit. Current load follows accepted #162 version `2026-09-11.3`: all tenant tickets assigned to that operator whose current status is open or pending, including waiting and snoozed work. Group-limited display totals never authorize a ceiling. Read endpoints disclose capacity only to the operator or a current administrator. Unconfigured operators retain prior manual behavior. Zero prevents additional normal assignments. Existing-owner no-ops do not require a new slot; reopen and ceiling reduction can leave existing load above the ceiling without silently dropping work.

Migration 0074 stores explicit available/unavailable state and a ceiling from 0 to 1000. Configuration uses expected revision, live administrator/session checks, retained budget authority, durable grant-operation recording and local-beta configuration accounting in one D1 batch. Revision increments are bounded by JavaScript's safe integer ceiling. An expired/revoked authority cannot leave a phantom completed operation. Configuration is not a new source of authentication or group permission. Target-user deletion cascades only its tenant-qualified capacity row; historical updated_by does not block author deletion. Native colliding-ID A/B deletion tests preserve other-tenant configuration. Existing unrelated user/group/ticket foreign-key restrictions remain unchanged; no tenant-deletion API is claimed.

Dashboard responsible-owner and route transitions check capacity within their existing canonical batch. An administrator may explicitly override availability/ceiling with a nonempty reason limited to 512 UTF-8 bytes. The internal canonical assignment event records reason, policy revision, availability and ceiling. Revision zero explicitly means no configured policy existed. Override cannot bypass existing tenant, staff eligibility, group or session checks. API assignment has no override.

Guard inventory: dashboard responsible-owner/route; canonical staff/API initial-owner creation; API audited update; direct ticket repository create, createWithInitialArticle and update when assigned_to is supplied. Existing path-specific eligibility and foreign keys remain in force. Legacy inbound creation currently supplies no assignee. No automatic routing or provider integration is enabled.

## Resource and release limitations

Dashboard update reserves an additional 4096 reads/4 writes; API create/update and staff create reserve another 2048 reads for the single bounded probe. The new index adds one entry on ticket creation/deletion and at most two replacement entries for a status/assignment change. Updated-at-only replies do not change its key. The corrected canonical write inventory explicitly includes all indexed-table exceptions: 500 receipt slots + 450 base mutation slots + 12 event + 8 ticket + 4 article + 2 support-state = 976, within the unchanged 1024-attempt ceiling. Canonical builders permit at most one ticket, two article and one support-state mutation per attempt. Native schema/write tests remain mandatory.

Capacity configuration writes reserve 2 KiB for their bounded row/index metadata; reads reserve no storage growth. This does not cover historical ticket-index backfill or inherited missing ticket-storage accounting under #64. For planning only, let P be the measured SQLite page size, U its usable bytes, N the candidate row count, and B each record's actual encoded text-key bytes plus a conservative 64-byte header/rowid allowance. A deliberately loose final-index allocation estimate is P × (2N + 1 + Σceil(B/(U−4))), allowing leaf/interior pages and overflow payload. This assumes ordinary SQLite B-tree/overflow layout and measured valid page parameters; it is not implemented stock admission or a substitute for native migration rehearsal. Separately allow temporary/sort space. Rehearsal must inventory actual legacy key bytes and resource limits before remote application.
