## Objective and decision

Establish a shared headless UI architecture for Tocyn's dashboard, customer portal and helpdesk widgets. Behavioural state machines must execute independently of visual styling. The same primitives and token contract must support the full standalone application and embedded widgets; embedding is an optional delivery mode, never a prerequisite for running Tocyn.

**Preferred foundation: Ark UI with Zag state machines, using the React adapter for the current React applications.** Ark supports React, Solid, Vue and Svelte, offers unstyled primitives and documents custom root environments. Zag supplies the framework-agnostic behaviour layer. This is a good fit for the requested separation and possible future framework adapters; Ark's React components themselves are not framework-independent Web Components. Base UI is also unstyled but targets React, making Ark/Zag the stronger fit for this particular cross-framework objective. Do not claim any library is universally the “most agnostic” or smallest without measuring it.

At implementation start, record the chosen stable Ark/Zag versions, React peer compatibility, licence and browser support in an architecture decision record. Prove a dialog, select/combobox and tooltip inside Shadow DOM before broad migration. If a blocking limitation appears, document it and propose an alternative against these same requirements rather than silently dropping them.

## Current baseline

Reviewed main `8ddd00ba7548f48ba4d461198adabb59fdd54a9e` (PRs #43, #46, #47). No Ark dependency is present in the client package manifests. `apps/widget/src/main.tsx` already mounts React into an open shadow root, but uses a singleton global container, placeholder styling and optional `window.LUMINA_WIDGET_CSS`. This does **not** establish a reusable custom element, a token API, reliable bundled styling or tested two-way CSS isolation. Evolve this implementation; do not count its existing `attachShadow` call as completion.

## Non-negotiable constraints

- **All design tokens must be standard CSS custom properties**, namespaced `--tocyn-*`: colours, typography, spacing, sizing, borders, radii, shadows, motion and stacking. Consume them with `var(...)` in ordinary static CSS. A typed token-name schema is acceptable; JavaScript theme objects must not become a separate styling engine or source of truth.
- **Runtime CSS-in-JS is explicitly forbidden** in Tocyn runtime code and dependencies used to style these components: no Emotion, styled-components, runtime style serialization, theme-to-rule generation, dynamic class/style-sheet generation or equivalent runtime styling system. Use authored CSS or CSS Modules compiled into static CSS assets. Ark does not require adopting a companion styling framework.
- Applying validated values to existing CSS custom properties through standard browser APIs is permitted. Loading a build-produced static stylesheet into a shadow root is permitted. Neither permission allows generating presentation rules at runtime. Ark's necessary DOM geometry/positioning updates are behaviour, not design tokens; document and test these separately.
- Keep behaviour, presentation and delivery adapters separate. No appearance-dependent state transitions, duplicate widget-specific interaction machines or colour/spacing values embedded in behaviour code. Prefer native HTML semantics for simple controls; use Ark primitives for supported complex interactions, with documented accessible extensions for gaps. Inventory **all** existing base components and migrate them; do not finish after a demonstration subset.
- Minimize browser JavaScript and Cloudflare edge startup work. Keep browser UI packages out of Worker API bundles; if an edge-rendered frontend is introduced, explicitly test that entrypoint. Pages static assets do not execute React inside Workers merely because they are hosted on Cloudflare. Measure bundle and startup effects instead of asserting a performance gain without evidence.

## Deliverable 1 — Ark UI foundation and extendable TypeScript primitives

- [ ] Introduce a shared package with separate public exports for headless primitives, static styles/tokens, and optional browser delivery adapters. Record dependency direction and prohibit server imports of browser-only entrypoints.
- [ ] Export documented, named, standard **extendable TypeScript interfaces for every public primitive and component part**, including supported native/ARIA props, refs, controlled/uncontrolled state, typed events, disabled/read-only states and composition hooks. Derive compatible Ark types without losing inference; no `any` escape hatch or opaque configuration blob. Include an example where a downstream interface extends a Tocyn primitive interface.
- [ ] Preserve Ark/Zag interaction and accessibility contracts independently of the visual layer. Include state transitions, keyboard handling, focus, labels, validation/error announcements, reduced motion and directionality. Complex domain/editor components may compose primitives; do not rewrite their application logic into Ark indiscriminately.
- [ ] Produce a component inventory and migration matrix covering dashboard, portal and widget base controls, including dialogs, menus, tooltips, popovers, selects/comboboxes, tabs, form fields and feedback. Record native-element and unsupported-component decisions explicitly; remove superseded ad hoc base behaviour after migration.
- [ ] Keep standalone routes, login, ticket create/list/detail and settings functional using normal document/container rendering. Share primitives and CSS with widgets; standalone startup must not require custom-element registration, a host application, iframe or widget loader.

## Deliverable 2 — Multi-tenant CSS variable injection

- [ ] Define a versioned public token schema with types/allowed values, defaults, fallback behaviour, precedence, light/dark and contrast expectations. Include at least `--tocyn-color-brand`, `--tocyn-color-on-brand`, `--tocyn-color-surface`, `--tocyn-color-text`, `--tocyn-color-border`, `--tocyn-color-focus`, `--tocyn-font-family`, `--tocyn-font-size-base`, `--tocyn-space-unit`, `--tocyn-radius-control` and `--tocyn-overlay-z-index`; enumerate the complete token set in documentation and a compile-checked name map.
- [ ] Apply tenant-specific tokens at `document.documentElement` for a single-tenant standalone document, or the relevant application container/custom-element host for scoped and embedded rendering. Support multiple differently themed tenant instances in one document without mutating another instance or the host page's root theme.
- [ ] Specify precedence: built-in fallback < tenant theme < explicit per-instance brand overrides. Resolve public values into internal tokens without shadow-local defaults accidentally masking inherited host overrides. Use internal fallback values for absent public properties; validate programmatically supplied values, including invalid CSS that would otherwise become invalid at computed-value time.
- [ ] Theme changes update only variables and must preserve machine state, focus and user input. Provide deterministic first paint without an incorrect tenant theme flash; support reset/removal of overrides and instance teardown.
- [ ] Select server-provided themes using the existing trusted tenant/authentication boundary. Theme IDs, public widget keys, CSS variables and host attributes grant no data access. Allowlist token names and validate typed values; never accept arbitrary CSS text, selectors, stylesheet URLs or executable theme payloads. Do not put credentials or private tenant data in CSS or static embed markup. Scope any theme caching by tenant and version.
- [ ] Document a CSP-compatible static-style loading and token-application strategy without requiring `unsafe-eval` or blanket `unsafe-inline`. Test the actual selected mechanism and policy. No runtime CSS-in-JS workaround is permitted.

## Deliverable 3 — Shadow DOM Web Component wrapper and brand API

- [ ] Provide a documented, versioned custom element (proposed `<tocyn-helpdesk>`) that mounts the shared React UI within its own Shadow DOM. Registration must be explicit/idempotent and browser-only. Support independent multiple instances, connect/disconnect/reconnect, complete cleanup of React roots, listeners and subscriptions, and typed configuration/events. Preserve or document a migration adapter for existing embeds.
- [ ] Bundle and load real static component CSS **inside each shadow root**, including resets and fonts as appropriate. Remove the global CSS-string dependency and placeholder-only styling. Do not inject widget reset/presentation rules into the outer document. If sharing immutable constructed stylesheets, document browser fallback and test it.
- [ ] Configure Ark's `EnvironmentProvider` for the instance root and direct every overlay/portal into that same shadow root. Include dialogs, popovers, tooltips, menus, combobox lists and toasts. Verify focus trapping/restoration, dismissal, positioning, clipping and scroll management; do not solve overlay positioning by leaking styled nodes into `document.body`.
- [ ] Completely isolate component presentation from incidental host CSS and prevent component styles changing host controls. Reset inherited presentation on an internal wrapper and deliberately specify typography, colour, line height, box sizing and direction handling. Consume only the documented public brand variables; initialise internal variables locally. Avoid accidental `::part`/slotted-content styling escape hatches; document any deliberate extension separately.
- [ ] Expose the defined CSS variable API **through the shadow boundary**. Host applications can map Ant Design, Material UI or shadcn brand tokens onto the custom element using standard CSS, without importing Tocyn's rendering framework or sharing their styling runtime. Example:

  ```css
  tocyn-helpdesk.support {
    --tocyn-color-brand: var(--host-brand, #2457d6);
    --tocyn-color-on-brand: #fff;
    --tocyn-font-family: system-ui, sans-serif;
    --tocyn-radius-control: 0.5rem;
  }
  ```

- [ ] Document the isolation contract precisely: CSS selectors cannot cross into internal component nodes, while the explicit public custom properties intentionally inherit through the host. Shadow DOM is not a security boundary against host JavaScript, nor can it stop a host deliberately hiding/removing/sizing the custom element. Do not claim protection against those actions. Test accidental inherited styles, not just selector isolation.

## Acceptance criteria — automated release gates

All three deliverables require CI evidence tied to the final revision:

1. **Type contracts and behavioural independence:** compile downstream `interface ... extends ...` examples for every public primitive; test controlled/uncontrolled transitions, events and refs. The same interaction suite passes with default CSS, a radically different valid theme and presentation CSS omitted. Accessibility semantics remain correct.
2. **Edge compatibility:** build the standalone clients and widget; run the actual Worker entrypoint in local workerd/Miniflare with synthetic bindings. Assert server/module imports do not evaluate `window`, `document`, `HTMLElement` or `customElements`, need browser shims, or pull UI styling engines into the Worker. Test SSR/hydration in that runtime if SSR is shipped; otherwise record static-client architecture explicitly. Production deployment is not an acceptance-test shortcut.
3. **Polluted-DOM CSS isolation:** real-browser tests in Chromium, Firefox and WebKit mount actual Ant Design, Material UI and shadcn host fixtures plus aggressive universal/tag/attribute selectors, resets, `!important` rules, fonts and conflicting generic variables. Compare computed styles and visual baselines inside the widget and on host controls before/after mounting and opening every overlay. No accidental visual changes in either direction. Assert every widget overlay remains within its instance shadow root. Host-fixture styling dependencies must stay in test fixtures, never Tocyn production bundles.
4. **Cross-boundary token injection:** map host-brand variables to the documented `--tocyn-*` API and assert computed values on actual shadow-internal controls and overlays. Test defaults, invalid/missing values, precedence, dynamic updates without state loss, override removal, dark mode and two simultaneously mounted tenants with conflicting themes. One tenant's change must not alter another instance or host controls.
5. **Standalone parity and accessibility:** end-to-end login, ticket creation/list/detail and settings run without widget registration. Both standalone and embedded modes pass automated accessibility checks and keyboard/focus tests, including shadow overlays and multiple instances. Record manual keyboard and screen-reader results alongside #21; an automated scanner alone is insufficient.
6. **Performance and policy enforcement:** record compressed JS/CSS sizes, widget lazy-load boundaries and edge bundle/startup baseline with reproducible commands; set numeric regression budgets in CI before merging. Inspect production dependency graphs and built output to reject runtime CSS-in-JS, global widget CSS leakage and accidental browser UI inclusion in API Workers. Exercise the documented CSP in browser tests. Report measurements and limitations, not assumed cold-start improvements.
7. **Lifecycle and migration:** test repeated registration, unmount/reconnect, resource cleanup and multi-instance isolation; publish examples for standalone, plain HTML embeds and the three host framework integrations. The migration matrix must account for every base component and the previous embed contract. Existing repository checks remain green.
