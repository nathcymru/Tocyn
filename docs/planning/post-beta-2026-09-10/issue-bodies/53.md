## Objective and dependencies

Two-way support conversations through tenant-owned Slack apps. Parent [#49](https://github.com/nathcymru/Tocyn/issues/49); blocked on [#51](https://github.com/nathcymru/Tocyn/issues/51) and [#50](https://github.com/nathcymru/Tocyn/issues/50). Do not require enterprise API subscriptions to send vendor replies: use the shared dispatcher.

## Technical specification

- [ ] Generate a Slack app manifest and guided tenant-admin setup for an internal app. Store the installed Bot User OAuth Token and signing secret encrypted per connection. Validate bot/workspace identity and selected channels during setup. Central Tocyn OAuth/marketplace distribution is deferred; do not silently add it back.
- [ ] Specify least-privilege scopes for configured channel types and `chat:write`; request private-channel scopes only when supporting configured private channels. Document app membership, Slack Connect workspace/channel identity and administrative approval requirements.
- [ ] Verify `X-Slack-Signature` against exact bytes and `X-Slack-Request-Timestamp`, including replay-age validation and constant-time verification. Match authenticated inner app/workspace identity to connection.
- [ ] Handle authenticated `url_verification` with the required challenge and HTTP 200 within Slack's 3-second deadline. Normal event acknowledgement follows Slack's contract after durable acceptance.
- [ ] Subscribe to `message.channels` and `app_mention` (and explicitly supported private channel events). Each top-level human message in configured channels creates a ticket; `thread_ts` replies append. Deduplicate overlapping subscriptions via stable IDs. Ignore bot/system/self-generated echoes; classify edits/deletions distinctly, not as new tickets.
- [ ] Preserve `team_id`, channel IDs, user IDs, `ts` and `thread_ts` as strings. Store message-to-ticket and provider-thread references.
- [ ] Send agent replies using `chat.postMessage` with the original channel and `thread_ts`, without detached new root messages. Handle API 429/backoff through the shared delivery policy.
- [ ] Handle `app_uninstalled` and applicable `tokens_revoked` as authenticated lifecycle events: atomically revoke affected connection/credential authority and stop future processing/dispatch. Do not let a revoked connection's stale cached ingress configuration authorise downstream writes.
- [ ] Document finite inbound retry behaviour and optional Slack delayed-events settings; do not promise that an ingress `Retry-After` pauses Slack indefinitely.

## Acceptance criteria

- [ ] Valid challenge returns correctly within deadline; invalid signatures/stale requests and wrong app/workspace fail without intake.
- [ ] Root/reply/mention fixtures create one ticket per root and append correctly under retries/reordering.
- [ ] Agent replies are threaded; bot echoes do not create tickets. Test shared-channel identities and unconfigured-channel exclusion.
- [ ] Uninstall/token revocation stops processing and dispatch, including queued events and cached ingress state.
- [ ] Test rate limits, cost rejection, quota cold path and unavailable vendor endpoints using synthetic fixtures.
