## Objective

Make efficient, bounded resource use a system-wide architectural boundary without weakening correctness. Cover existing application paths and future plugins. Establish the policy contracts before the omnichannel consumer is implemented.

## Accepted policy

- **Conservative is the default.** Disable optional work as its allocation is consumed. **Aggressive is explicit:** optional AI/nonessential background work default off; intake and attachment limits may be tighter.
- Deployment owner sets account budgets and tenant ceilings. Tenant administrators may lower limits, choose stricter modes or disable channels, never increase owner ceilings. Enforce this on the server; ordinary tenant admins must not acquire platform authority. Add a separately authorised deployment-owner identity boundary.
- Never reduce authentication, tenant isolation, durable acknowledgement, required security controls or recovery capacity to save money. Do not delete customer history merely because capacity is low.
- No automatic paid overage, plan upgrade or conditional billing mechanism. These controls govern Tocyn's admitted workload; they cannot guarantee a zero Cloudflare bill or account for unrelated workloads without an owner allocation.
- **Strict admission is the final decision:** consume preallocated capacity on the fast path; replenish on a miss or reject visibly. Do not optimistically enqueue unreserved work based only on a cached exhaustion flag. A slower cold path is preferable to violating the agreed ceiling.

## Technical specification

### Settings, authorisation and public contracts

- [ ] Add owner and tenant Cost & Capacity views: mode, assigned/effective ceilings, usage, reservations, estimates, data freshness, reset time, rejected intake and affected features.
- [ ] Export typed `CostPolicy`, `ResourceBudget`, `BudgetReservation`, `UsageSnapshot` and admission-result contracts. Store versioned policies, tenant allocations and durable reservation records separately from channel credentials. Server validation enforces tenant limit <= owner ceiling.
- [ ] Audit policy changes with actor, scope, before/after and time. Tenant responses cannot expose another tenant's usage or platform credentials.
- [ ] Apply the policy to ingestion, API writes, AI, indexing, exports, media, webhook retries, realtime activity and background jobs. Catalogue every metered active path; no bypass through a different endpoint.

### Reservations and accounting

- [ ] Model dimensions separately: Worker requests/CPU, Queue operations, D1 reads/writes/storage, R2 storage/Class A/Class B operations, DO requests/duration/storage operations, and AI neurons/model units.
- [ ] Introduce a dated/versioned allowance catalogue. Use actual provider reset periods rather than assuming all allowances reset monthly or at the same time. Expose estimated vs measured values; price estimates are not billing guarantees.
- [ ] Default new-work allocation to 80% of the owner's declared available capacity; reserve 20% for recovery, security and notification operations. Account for other applications and already accepted work. Owner changes are explicit and audited.
- [ ] Use durable quota coordination to allocate bounded blocks of admission credits, not a central RPC for every warm-path request. Each block is uniquely owned, versioned and bounded by resource/window. Grants must never collectively exceed the durable allocation. Lost/uncertain credits are not prematurely reissued. A missing/exhausted grant triggers replenishment or rejection.
- [ ] Reserve a bounded processing/retry/recovery envelope before intake; reserve outbound intent capacity with its originating mutation. Meter actual resource use and reconcile safe surplus. Include the overhead of the budget system itself.
- [ ] Use D1 query metadata where available, including index writes. Where precise advance usage is unknowable, enforce conservative workload caps and label resource estimates; never claim exact Cloudflare accounting from application counters alone.
- [ ] Cloudflare rate-limit bindings provide abuse controls, not exact global accounting. An unavailable/stale admission authority must not permit new discretionary work. Accepted messages retain reserved recovery capacity.

### Degradation and alerts

- [ ] **Gratitude classification is the first optional AI feature shed** under Conservative as AI capacity tightens; then other optional enrichment yields to deterministic/manual triage. Aggressive disables these by default. Fallback creates normal new-ticket work; it does not silently suppress a request or reopen the closed ticket.
- [ ] Bound AI input and use task-appropriate models. DistilBERT SST-2 is sentiment-only, not a gratitude classifier. No full-history prompt merely to classify a short reply. Report model/task quality as well as cost.
- [ ] When insufficient capacity remains, reject before durable acknowledgement using each provider's retry contract. For public API quotas return 429 with a documented reset hint. Do not assume Slack inbound webhook retries obey outbound Slack API `Retry-After` semantics.
- [ ] Deduplicate threshold/first-rejection alerts. Provide persistent dashboard state and a configured external notification route using reserved capacity. Surface notification failure. A dashboard notification is not an independent out-of-band channel.
- [ ] Warn explicitly: provider retries are finite, refused messages may never reach Tocyn, and Aggressive mode reduces availability/features. Do not promise that a free-tier ceiling or a $5 plan guarantees the core SLA.

### Storage and lifecycle

- [ ] Use canonical R2 bodies/media for new omnichannel work, with D1 metadata and scoped references. Assess existing body-storage paths before any historical migration; preserve compatibility and document search effects. Do not claim pointer storage makes arbitrary scans cheap.
- [ ] Bound raw-payload retention independently of ticket retention. Never expire the only recoverable copy of an unprocessed acknowledged event. Provide capacity warnings before storage exhaustion; no silent retention-policy shortening.
- [ ] Use DO hibernation and small durable coordination records. No memory-only acknowledged message buffer, global ingestion DO, or flush-on-WebSocket-close durability dependency.

## Acceptance criteria

- [ ] Concurrent reservations, lease exhaustion/loss, policy changes and reset-boundary races cannot over-allocate configured admission credits.
- [ ] Tenant admins cannot increase owner ceilings or affect another tenant; approved owner changes are audited.
- [ ] Warm requests spend reserved credits without a central quota RPC; cold/exhausted requests replenish or reject with measured latency.
- [ ] AI disabled/exhausted, storage pressure, query failure and notification failure preserve authentication and accepted-message recovery.
- [ ] Tests show gratitude classification sheds first and ambiguous gratitude becomes normal work.
- [ ] Usage panels distinguish actual/estimated/reserved and demonstrate daily/monthly resets with synthetic clocks.
- [ ] Test the catalogue against dated sources: Queues 10,000 operations/day and 24h free retention; D1 500 MB/database and separate row limits; SQLite DO 5 GB total; R2 Standard storage/operation allowances; Workers AI 10,000 neurons/day (not inferences). Free HTTP CPU allowance is separate from wall-clock latency.
- [ ] Document measured workload capacity, operational reserve and cost per representative flow. Full existing checks remain green.
