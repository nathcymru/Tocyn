# #133 durable activity backend foundation

- **Branch/base:** `codex/133-durable-activity-foundation` from accepted `0b144f80`.
- **Scope delivered:** additive `0038_operator_activity.sql`; bounded actor-recipient activity contract, tenant-scoped repository and service seam. Existing CI now invokes its focused native test and typecheck. No route, dashboard, NotificationDO, preferences, provider, canonical conversation, or retention-policy change is included.
- **Kinds:** `assignment`, `mention`, `customer_reply`, `sla_risk`, `resurfaced_work`, and `delivery_intervention`.
- **Authority:** the current authenticated recipient is checked in every list/count/read/dismiss operation against tenant, staff role, session version, expiry and current ticket-group membership. Admins retain existing cross-group staff access; no team recipient permission is introduced.
- **Production contract:** trusted producers provide a stable source ID, recipient, ticket and compact primitive facts. Idempotency is per tenant, recipient, kind and source, so one canonical source may project to multiple authorized actors. A SHA-256 immutable receipt fingerprint permits only exact replay; a conflicting prepared append aborts its entire canonical D1 batch. `prepareTrustedAppend()` returns the statement after asynchronous fingerprint preparation. `appendTrusted()` is a convenience for independent bounded server work. Neither method implies a successful post-commit WebSocket/provider delivery.
- **Bounds and authority:** list and unread count take at most 101 indexed tenant/recipient candidates. A larger candidate set returns explicit `recipient_activity_candidate_cap_exceeded` unavailable state rather than a partial queue or inexact count. Presentation credentials require matching scope and current session version, current staff role, expiry and MFA-authenticated provenance; every result also rechecks current ticket-group access.
- **Lifecycle:** deleting a ticket or recipient cascades its projection. A deleted staff producer retains `staff` provenance with a null/redacted ID and an opaque receipt fingerprint; a deleted-producer exact replay remains valid, while a changed receipt conflicts. No activity retention/deletion timer was invented. The producer-redaction index avoids a full projection scan; high deletion fanout remains an operational lifecycle concern for later production sizing.
- **Evidence:** `npm run test:operator-activity`, `npm run typecheck:operator-activity`, and `npm run typecheck --workspace=apps/server` pass with Node 22. The native Miniflare D1 proof covers two tenants with colliding IDs, multiple recipients for one source, recipient isolation, duplicate/concurrent source replay and per-recipient conflict, canonical-batch rollback on conflict, bounds/cursors, read/dismiss CAS, revoked session/stale scope/current group membership, deleted producer receipt replay, deleted tickets, capped inaccessible backlog, and both candidate index query plans.
- **Integration next action:** #70 must call the prepared append statement in its canonical internal-mention batch only after its own parser/recipient authorization succeeds. #130 may use `OperatorActivityService.list`, `unreadCount`, `markRead`, and `dismiss` with the current staff credential. Future system SLA/customer-reply producers retain independent recipient/ticket authorization at their own canonical commit.
- **Known boundary:** the existing ticket lifecycle is physical deletion with cascades; no soft-delete/tombstone contract exists for activity to interpret. UI interruption preferences remain owned by #132/#133's later acceptance work.
