- **Kinds:** `assignment`, `mention`, `customer_reply`, `sla_risk`, `resurfaced_work`, and `delivery_intervention`.
- **Authority:** the current authenticated recipient is checked in every list/count/read/dismiss operation against tenant, staff role, session version, expiry and current ticket-group membership. Admins retain existing cross-group staff access; no team recipient permission is introduced.
- **Production contract:** trusted producers provide a stable projection ID and source ID, recipient, ticket and compact primitive facts. Every retry must reuse both IDs and every immutable field; generating a fresh projection ID for an existing source is an explicit conflict. Idempotency is per tenant, recipient, kind and source, so one canonical source may project to multiple authorized actors. A SHA-256 immutable receipt fingerprint permits only exact replay; a conflicting projection-ID or source reuse aborts its entire canonical D1 batch. Only the exact source uniqueness conflict is ignored; other insert/constraint failures remain failures. The duplicate fallback rechecks live recipient/ticket authority. `prepareTrustedAppend()` returns the statement after asynchronous fingerprint preparation. `appendTrusted()` is a convenience for independent bounded server work. Neither method implies a successful post-commit WebSocket/provider delivery.
- **Bounds and authority:** each list request uses an indexed tuple seek and 100 tenant/recipient candidates plus one lookahead, returning at most 50 authorized items. Sparse/empty pages carry a continuation when more candidates remain; consumers must continue until `next` is null and must not interpret an empty page as end-of-history. Cursors use authenticated encryption and a purpose-separated HKDF key derived from the existing server JWT secret, bind tenant/actor/authVersion, and expire after at most 15 minutes or the credential expiry. Missing/rotated keys, tampering, changed authority and expired cursors fail closed with an explicit pagination-restart error. Exact unread count alone retains explicit `recipient_activity_candidate_cap_exceeded` unavailability above 100 unread candidates until a later scalable visibility/count model exists. Presentation credentials require matching scope/current session version, current staff role, expiry, MFA-authenticated provenance and live `mfa_enabled=1`; every result also checks current ticket-group access.
- **Lifecycle:** deleting a ticket or recipient cascades its projection. A deleted staff producer retains `staff` provenance with a null/redacted ID and an opaque receipt fingerprint; a deleted-producer exact replay remains valid, while a changed receipt conflicts. No activity retention/deletion timer was invented. The producer-redaction index avoids a full projection scan; high deletion fanout remains an operational lifecycle concern for later production sizing.
- **Prior foundation evidence:** `npm run test:operator-activity`, `npm run typecheck:operator-activity`, and `npm run typecheck --workspace=apps/server` pass with Node 22. The native Miniflare D1 proof covers two tenants with colliding IDs, multiple recipients for one source, recipient isolation, duplicate/concurrent source replay and per-recipient conflict, canonical-batch rollback on conflict, bounds/cursors, read/dismiss CAS, revoked session/stale scope/current group membership, deleted producer receipt replay, deleted tickets, the original capped backlog contract and simplified candidate index plans.
